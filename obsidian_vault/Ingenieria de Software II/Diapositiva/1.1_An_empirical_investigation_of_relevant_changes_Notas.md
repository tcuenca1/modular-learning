# An empirical investigation of relevant changes and automation needs in modern code review

[[Ingenieria de Software II]]

## Abstract

Recent research has shown that available tools for [[Modern Code Review]] ([[MCR]]) are still far from meeting the current expectations of developers. The objective of this paper is to investigate the approaches and tools that, from a developer’s point of view, are still needed to facilitate [[MCR]] activities. To that end, we first empirically elicited a taxonomy of recurrent review change types that characterize [[MCR]]. The taxonomy was designed by performing three steps: (i) we generated an initial version of the taxonomy by qualitatively and quantitatively analyzing 211 review changes/commits and 648 review comments of ten open-source projects; then (ii) we integrated into this initial taxonomy, topics, and [[MCR]] change types of an existing taxonomy available from the literature; finally, (iii) we surveyed 52 developers to integrate eventually missing change types in the taxonomy. Results of our study highlight that the availability of new emerging development technologies (e.g., [[Cloud-based technologies]]) and practices (e.g., [[Continuous Delivery]]) has pushed developers to perform additional activities during [[MCR]] and that additional types of feedback are expected by reviewers. Our participants provided recommendations, specified techniques to employ, and highlighted the data to analyze for building recommender systems able to automate the code review activities composing our taxonomy. We surveyed 14 additional participants (12 developers and 2 researchers), not involved in the previous survey, to qualitatively assess the relevance and completeness of the identified [[MCR]] change types as well as assess how critical and feasible to implement are some of the identified techniques to support [[MCR]] activities. Thus, with a study involving 21 additional developers, we qualitatively assess the feasibility and usefulness of leveraging [[Natural Language Processing]] ([[NLP]]) feedback (automation considered critical/feasible to implement) in supporting developers during [[MCR]] activities. In summary, this study sheds some more light on the approaches and tools that are still needed to facilitate [[MCR]] activities, confirming the feasibility and usefulness of using summarization techniques during [[MCR]] activities. We believe that the results of our work represent an essential step for meeting the expectations of developers and supporting the vision of full or partial automation in [[MCR]].

## 1. Introduction

[[Modern Code Review]] ([[MCR]]) represents a variant of the traditional code review (CR) process, whose main characteristic is to be informal and supported by tools. Nowadays, [[MCR]] is a widely applied practice in both open-source and industrial systems, and recent work empirically investigated its process outcomes, its available tools, or proposed solutions to automate some of its activities.

During [[MCR]], developers are usually interested in improving the quality of submitted patches by fixing bugs, adhering to conventions/coding styles or by making the source code easier to be maintained, to meet user expectations. In this process, a developer, author of the code under review, asks other developers (i.e., the reviewers) to inspect her/his code.

[[MCR]] is generally supported by tools aiding developers during various activities. For example, the [[Gerrit]] tool is widely used by open-source projects to support the management of the [[MCR]] process, while [[CheckStyle]] and [[PMD]] are popular tools used for detecting defects (e.g., Vulnerabilities) and design issues (e.g., high coupling between objects) in the code under review.

Recent research produced further tools to support decisions and actions of [[MCR]]: recommender systems (i) selecting appropriate peer reviewers to evaluate a given patch and approaches to automatically (ii) decompose code review change-sets, recommending the files to focus on during a review, or to simply detect potential mistakes. However, according to recent research, outcomes of available tools and prototypes are still far from meeting the current expectations of developers in modern code review.

The objective of this paper is to investigate the approaches and tools that, from a developer point of view, are still needed to facilitate [[MCR]] activities. With *code review changes* (or *code review change types*), we explicitly refer to the actual "changes that developers perform to address the received code review comments".

### Research Questions
1. **$RQ_1$: What types of changes occur during [[MCR]]?**
   We first empirically elicited a taxonomy of the most critical and recurrent [[MCR]] change types that characterize reviews and investigated the types of [[MCR]] changes that, according to the developers involved in our study, could (or should) be automated.
2. **$RQ_2$: What are the emerging automation needs of developers in [[MCR]]?**
   Here we investigate the data, approaches and tools that developers would need to accommodate the identified [[MCR]] change types.

## 2. Research Methodology

> **Diagrama detectado:** Figura 1 muestra una descripción general del enfoque de investigación que consta de cuatro fases:
> 1. *Inception Phase*: Recopilación de información sobre tipos específicos de cambios en [[MCR]] analizando datos de [[Gerrit]], código fuente, aspectos humanos/sociales, encuestas previas y taxonomías existentes.
> 2. *Taxonomy Definition ($RQ_1$)*: Encuesta a 52 desarrolladores para validar y obtener retroalimentación, derivando el modelo de cambios de revisión de código ([[CRAM]]).
> 3. *Automation Needs in [[MCR]] ($RQ_2$)*: Preguntar a los participantes sobre procesos, prácticas y herramientas necesarias para manejar los cambios de [[CRAM]].
> 4. *Recommendations, Techniques, and Solutions ($RQ_2$)*: Construcción del modelo MCR-Request agrupando retroalimentación en recomendaciones, técnicas y soluciones (ej. uso de predicción de cambios, auto-correcciones, métricas de CR, patrones, etc.).

### 2.1 Approach Overview
The methodology is divided into four main steps:
- **Inception Phase:** Analysis of commits and comments from 10 open-source Java projects (e.g., [[Eclipse Acceleo]], [[Eclipse CDT]], [[Eclipse Amalgam]], [[JGit]], [[M2e]], etc.) considering periods between 2012 and 2017. A grounded theory approach was applied to 648 reviewers' comments related to 211 [[MCR]] commits, identifying 15 initial potential change types.
- **Taxonomy Definition ($RQ_1$):** A survey involving 52 developers (using [[Google Forms]]) to validate the taxonomy, resulting in the **Code Review chAnges Model ([[CRAM]])**.
- **Automation Needs in [[MCR]] ($RQ_2$):** Evaluation of tools and practices needed to handle changes.
- **Recommendations, Techniques, and Solutions ($RQ_2$):** Clustering feedback into the **MCR-Request** model (Recommendations, Techniques, and Solutions).

## 3. Results

### 3.1 $RQ_1$: Types of Changes Occurring in Modern Code Reviews
The first survey yielded 52 responses. Most participants considered themselves "very good" (32.7%) or "excellent" (46.2%) programmers, with over 67% having more than 8 years of experience.

The resulting taxonomy, **Code Review chAnges Model ([[CRAM]])**, classifies changes across multiple dimensions:
- **Artifact Type:** Test code, production code, configuration files, non-source-code artifacts.
- **Activity Types:** Perfective maintenance, corrective maintenance, maintainability, functionality.
- **Categories & Detailed Topics:** 
  - **Documentation (D):** Naming (D.1), Comments (D.2), License Header (D.3), Typos (D.4), Other (D.5).
  - **Style (S):** Immutability (D.6), Visibility (D.7), Brackets & Braces (S.1), Indentation (S.2), Blank Lines (S.3), Long Lines (S.4), Whitespace Usage (S.5), Grouping (S.6), Commented out code (S.7).
  - **Structure (STR):** Semantic Duplication (STR.1), Semantic Dead Code (STR.2), Change Function (STR.3), Standard Coding Conventions (STR.4), New Functionality (STR.5), Strings/Wording (STR.6), Logging (STR.7), Testing (STR.8), Imports (STR.9), Move Functionality (STR.10), Long Sub Routine (STR.11), Dead Code (STR.12), Duplication (STR.13), Complex Code (STR.14), Statement Issue (STR.15), Consistency (STR.16), Architectural changes (STR.17).
  - **Functionality / Logic / Resource / Check / Larger Defects (LD):** Includes performance, security ([[Security issues]]), concurrency, memory management, and GUI/completeness issues.
  - **Other Changes (Non-source-code artifacts):** Commit Messages (O.1), [[Continuous Integration]] / [[Continuous Delivery]] configurations (O.2), Static Analysis Tools configurations (O.3), Language/Framework specific files (O.4), External Software Documentation (O.5), Runtime Configurations (e.g., [[Docker]] files) (O.6), Other (XML, Scripts, README, Version Control) (O.7).

### 3.2 $RQ_2$: Emerging Automation Needs in [[MCR]]
- **Frequent vs. Expected Feedback:** Structure and Documentation are the most frequent change topics, while Functionality-related issues (such as performance, resources, and security) are increasingly expected by developers.
- **Envisioned Solutions:** Developers demand automated tools for:
  - Automatically detecting and fixing documentation issues and generating missing documentation or license headers.
  - Advanced refactoring recommendations for test and production code.
  - Automated detection and patching of performance bottlenecks, resource consumption, and security flaws.
  - Recommending, improving, and monitoring [[Continuous Integration]] / [[Continuous Delivery]] pipelines and static analysis configurations.
- **Role of Summarization Techniques:** The study proposes and evaluates an approach for automatically generating test smell summaries (focusing on smells like *LongParameterList* and *LongMethod*) using tools like [[DECOR]] and [[TACO]], combined with the Software Word Usage Model ([[SWUM]]). Qualitative evaluations via an offline experiment with 21 participants showed that test smell summaries are easy to understand and serve as a useful source of information to improve test suite quality during [[MCR]].

## 4. Threats to Validity
- **Construct Validity:** Addressed by discarding incomplete/ambiguous responses and using multiple independent sources for constructing [[CRAM]].
- **Internal Validity:** Minimized taxonomy omissions by grouping change types into high- and low-level categories.
- **External Validity:** Limited to 10 Java open-source projects (within the Eclipse ecosystem) and 52 developers. Future work aims to expand to more projects and programming languages.
